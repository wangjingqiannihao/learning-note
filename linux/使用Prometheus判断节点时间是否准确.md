# 使用 Prometheus 判断节点时间是否准确

## 结论

判断节点时间是否准确，不能只看一个偏移指标。推荐采用三层判断：首先通过 node_exporter 的 timex 指标确认内核是否处于同步状态并监控偏移；其次明确 `node_timex_offset_seconds` 是内核时间校正状态中的估计偏移，不是一次实时网络测量；最后通过多时钟源、跨节点对比和独立可信基准，防止所有节点同步到同一个错误时间源却未触发告警。

## 使用 node_exporter 判断节点是否同步

node_exporter 的 timex collector 从 Linux 内核的 `adjtimex` 接口读取时间同步状态。节点级监控至少需要关注以下指标：

- `node_timex_sync_status`：内核是否认为本机时钟已同步。值为 1 表示同步，值为 0 表示未同步。
- `node_timex_offset_seconds`：内核时间控制环当前使用的时钟偏移估计，单位为秒。
- `node_timex_maxerror_seconds`：内核估计的最大时间误差，单位为秒；持续增大说明同步质量下降或已经失去有效更新。
- `node_timex_estimated_error_seconds`：内核估计的当前时间误差，单位为秒，可作为辅助判断依据。

告警应将“同步状态异常”和“偏移超过业务容忍范围”分开处理。前者说明节点没有可靠同步，后者说明即使处于同步状态，时间误差仍然过大。阈值应按业务要求设置：普通日志与监控场景可使用秒级或百毫秒级阈值；分布式数据库、租约、证书校验和严格事件排序应采用更小的阈值。

```yaml
# Prometheus 告警规则示例。
groups:
  - name: node-time
    rules:
      # 内核未处于同步状态，持续 5 分钟后告警。
      - alert: ClockNotSynchronised
        expr: node_timex_sync_status == 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "节点时钟未同步"
          description: "节点 {{ $labels.instance }} 的内核时钟未处于同步状态。"

      # 偏移绝对值超过 100 ms，持续 5 分钟后告警。
      # 100 ms 仅为示例，应根据业务容忍度调整。
      - alert: ClockSkewDetected
        expr: abs(node_timex_offset_seconds) > 0.1
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "节点时钟偏移过大"
          description: "节点 {{ $labels.instance }} 的内核时钟偏移绝对值超过 100 ms。"

      # 最大误差持续超过 1 秒时告警，用于识别同步质量恶化。
      - alert: ClockMaximumErrorTooHigh
        expr: node_timex_maxerror_seconds > 1
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "节点时钟最大误差过大"
          description: "节点 {{ $labels.instance }} 的最大时间误差持续超过 1 秒。"
```

查询时不要只判断瞬时值。使用 `for` 持续时间可以减少网络抖动、服务重启和时钟源切换带来的短时误报。还应结合 `up` 指标区分“节点确实异常”和“指标未采集到”。

## 如何理解 node_timex_offset_seconds

`node_timex_offset_seconds` 可以理解为本机时钟相对于 chronyd 或 ntpd 当前选定时间源的偏移估计，但它不是 exporter 主动向时间源发起探测后得到的即时差值。chronyd 或 ntpd 先测量上游时间源，再根据滤波、源选择和校正算法更新内核的时间控制参数；node_exporter 最后从内核读取这个状态。

因此，该指标具有两个重要限制：

1. 它反映的是经过时间同步守护进程和内核 PLL/FLL 平滑处理后的状态，不等同于最近一次 NTP 报文测得的瞬时偏移。
2. 它主要回答“本机内核正在如何校正时间”，不能完整说明各候选时间源的质量、延迟、抖动和选源结果。

需要更接近 chronyd 当前判断的数据时，可以查看 `chronyc tracking`：

```bash
# 查看 chronyd 当前跟踪状态。
chronyc tracking
```

其中：

- `System time` 表示系统时钟相对于 chronyd 估计正确时间的差值。
- `Last offset` 表示上一次时钟更新时测得的偏移。
- `RMS offset` 表示长期偏移的均方根估计。

排障时可以继续使用以下命令查看每个候选源的选择状态、偏移、抖动和样本质量：

```bash
# 查看候选时间源及其当前选择状态。
chronyc sources -v

# 查看候选时间源的统计信息。
chronyc sourcestats -v
```

## 时钟源本身错误时如何防御

如果唯一上游时钟源给出了错误时间，单节点上的 `node_timex_sync_status` 仍可为 1，偏移也可很小，因为节点只是“成功同步到了错误基准”。因此，Prometheus 不能仅根据单节点与其选定源的相对偏移证明绝对时间正确。

### 时间同步层的防御

配置至少 4 个独立且来源不同的时钟源，让 chronyd 或 ntpd 基于多数一致性、距离、抖动和历史稳定性选择可信源，并把明显偏离多数结果的源标记为异常源。时钟源不应全部位于同一管理域、同一网络链路或同一上游层级，否则多个配置项仍可能共享同一个故障点。

对防篡改有要求时，可以使用 NTS 或受控环境中的密钥认证，降低伪造和中间人修改 NTP 响应的风险。

还应设置大幅跳时保护，避免异常源导致系统时钟突然跳变。chronyd 的具体策略需要结合启动阶段和运行阶段区分：启动时可以允许有限次数的步进校时，稳定运行后则应对异常大偏差进行拒绝、告警或人工确认。保护阈值必须与业务对时间跳变的容忍度一致。

### 监控层的防御

Prometheus 应从单节点判断升级为群体和基准交叉校验：

- 横向比较同一集群或同一区域的节点。如果大多数节点稳定，少数节点偏离，可定位节点级故障；如果大量节点同时发生同方向偏移，应优先检查共享上游源或网络路径。
- 引入独立可信基准，例如独立管理域的 Stratum-1、GNSS/GPS 授时设备或其他经过验证的时间服务，用于校验集群整体是否发生共同偏移。
- 采集 chronyd 的源级指标，而不是只采集内核 timex 状态。通过 chrony exporter 或等效采集方式监控每个候选源的状态、偏移、延迟、抖动、层级和可达性。
- 对“选中源发生变化”“可用源数量不足”“多数源之间分歧扩大”“所有节点同步正常但相对独立基准整体偏移”等情况建立独立告警。

完整的判断链路应是：内核同步状态正常、节点偏移在业务阈值内、候选时间源数量和质量正常、节点群体之间没有异常分叉，并且集群相对独立可信基准没有整体偏移。只有这些条件同时满足，才能对节点时间准确性给出较强判断。

## 推荐落地顺序

1. 启用 node_exporter 的 timex collector，确认 Prometheus 能采集同步状态、偏移和误差指标。
2. 按业务容忍度设置未同步、偏移过大和最大误差过大的告警，并配置持续时间抑制瞬时抖动。
3. 为 chronyd 或 ntpd 配置至少 4 个不同管理域的时间源，并检查异常源剔除和大幅跳时保护策略。
4. 部署 chrony exporter 或等效采集器，将候选源明细纳入监控。
5. 增加跨节点横向对比，并引入独立可信基准，覆盖“集体同步到错误时间源”的盲区。

## 边界与注意事项

Prometheus 的采集数据本身带有时间戳，严重时钟偏差会影响样本写入、查询窗口和告警判断。对于高风险场景，应同时从监控系统侧检查样本时间异常和采集延迟。

虚拟机、容器宿主机与来宾系统也可能存在不同授时路径，必须明确由宿主机、来宾系统还是两者共同负责校时，避免多个机制相互竞争。

本文中的 100 ms 和 1 s 均为示例阈值，不代表通用标准。最终阈值应由业务对日志排序、分布式一致性、证书有效期、令牌校验、数据库事务和故障切换的要求决定。
