# 主流消息队列对比

## 结论

RocketMQ、Kafka、RabbitMQ、Pulsar 和 NATS 没有绝对的优劣，主要差异在于产品定位：

| 需求 | 推荐选择 | 原因 |
| --- | --- | --- |
| 订单、支付、库存等业务消息 | RocketMQ | 事务、顺序、延迟和消息追踪能力完整 |
| 日志采集、CDC、数据管道和流处理 | Kafka | 吞吐高，消息回溯和数据生态成熟 |
| 中小规模异步任务、复杂消息路由 | RabbitMQ | 路由灵活，协议和跨语言支持成熟 |
| 云原生多租户、跨地域消息平台 | Pulsar | 原生支持多租户、存算分离和跨地域复制 |
| 微服务、边缘节点和低延迟通信 | NATS | 轻量、低延迟，部署简单 |

典型 Java 业务系统如果需要事务消息、顺序消息和延迟消息，优先评估 RocketMQ；海量事件流和数据处理优先评估 Kafka；复杂路由和普通任务队列优先评估 RabbitMQ。

## 能力对比

| 对比项 | RocketMQ | Kafka | RabbitMQ | Pulsar | NATS / JetStream |
| --- | --- | --- | --- | --- | --- |
| 核心定位 | 业务消息 | 事件流与分布式日志 | 通用消息代理 | 云原生消息与事件流 | 轻量低延迟消息 |
| 吞吐能力 | 很高 | 极高 | 中等 | 很高 | 很高 |
| 单条消息延迟 | 低 | 中低，偏向批量 | 低 | 低 | 极低 |
| 大规模消息积压 | 强 | 极强 | 一般 | 极强 | 中等至强 |
| 事务消息 | 原生支持，适合业务事务 | 支持 Kafka 内部事务 | 支持 AMQP 事务和发布确认 | 支持 | 相对有限 |
| 顺序保证 | 队列内有序 | 分区内有序 | 单队列可有序 | 分区内有序 | 支持有序消费 |
| 延迟或定时消息 | 原生支持 | 通常需要额外实现 | TTL、死信队列或插件 | 原生支持 | JetStream 支持 |
| 消息路由 | Tag、属性过滤 | Topic、分区 | Exchange 路由非常灵活 | Topic、订阅模式 | Subject 通配符 |
| 消息回溯 | 支持 | 非常成熟 | 不适合长期回溯 | 非常成熟 | JetStream 支持 |
| 多租户 | 一般 | 需要额外治理 | Virtual Host | 原生支持 | Account 隔离 |
| 运维复杂度 | 中等 | 中等 | 较低至中等 | 较高 | 较低 |
| 典型生态 | Java 业务系统 | 大数据与流处理 | 跨语言业务系统 | 云原生消息平台 | 微服务与边缘计算 |

表中的吞吐和延迟是典型定位，不代表固定性能。实际表现取决于消息大小、批量参数、可靠性级别、副本数、磁盘、网络和客户端配置，正式选型前仍需根据业务模型压测。

## RocketMQ

### 优点

RocketMQ 面向业务消息设计，原生支持事务消息、顺序消息、延迟消息、重试和死信队列。事务消息通过半消息和事务状态回查，处理本地事务与消息发送的一致性问题，适合订单、支付和库存等场景。

RocketMQ 支持根据 Message ID 和业务 Key 查询消息及消费轨迹，故障排查比较方便。它也能承载高并发和较大规模的消息积压，并且与 Java、Spring 生态结合成熟。

### 缺点

RocketMQ 的流处理和数据集成生态不如 Kafka。非 Java 客户端的成熟度和使用规模通常也不如 Java 客户端。集群部署、参数配置和版本升级需要一定运维经验；对于简单任务队列，整体架构可能偏重。

### 适用场景

适合订单状态流转、支付通知、库存扣减、延迟关单、业务事件解耦，以及需要事务、顺序或延迟语义的系统。

## Kafka

### 优点

Kafka 的优势是高吞吐、持久化日志和消息回溯。追加写和批量传输机制适合日志、埋点、数据库变更和实时计算。消息可以按时间或容量长期保留，消费者能够重复读取历史数据。

Kafka 与 Flink、Spark、Debezium、Kafka Connect 和数据仓库的集成广泛，适合构建数据管道和事件流平台。

### 缺点

Kafka 更接近分布式事件日志，而不是传统业务消息队列。延迟消息、单条消息重试、死信处理和复杂路由通常需要额外设计。它只能保证分区内有序，增加分区后不能保证全局顺序。

Kafka 的事务主要解决 Kafka 内部多分区写入和消费处理的一致性，不等同于 RocketMQ 面向本地数据库事务的回查机制。

### 适用场景

适合日志采集、用户行为埋点、CDC、实时计算、数据湖导入、事件溯源，以及需要长期保留和重复消费的数据流。

## RabbitMQ

### 优点

RabbitMQ 通过 Direct、Topic、Fanout 和 Headers 等 Exchange 提供灵活的消息路由。它对 AMQP 等协议支持较好，跨语言客户端成熟，消息确认、消费者限流、优先级队列和管理界面也比较完善。

对于吞吐规模适中的系统，RabbitMQ 部署和使用相对直观。

### 缺点

RabbitMQ 不以超大规模消息积压和日志留存为主要目标。队列长期堆积大量消息时，性能和运维压力通常比 Kafka、RocketMQ 更明显。延迟消息一般通过 TTL、死信队列或插件实现；并发消费和重新投递场景下，需要额外控制消息顺序。

### 适用场景

适合异步任务、后台作业、通知发送、复杂路由、异步 RPC，以及强调低延迟和跨语言兼容的中小规模系统。

## Pulsar

### 优点

Pulsar 采用存算分离架构，Broker 负责协议和计算，BookKeeper 负责持久化存储，可以独立扩展计算和存储资源。它原生支持多租户、命名空间、跨地域复制、多种订阅模式和长期消息保留。

### 缺点

Pulsar 的组件较多，架构和运维复杂度通常高于 RocketMQ、Kafka 和 RabbitMQ。Broker、BookKeeper 和元数据组件都需要监控和治理，对小团队的成本较高。社区规模和工程实践的普及程度也不如 Kafka。

### 适用场景

适合大型云原生平台、多租户消息平台、跨地域消息复制、海量 Topic，以及同时承载业务消息和事件流的系统。

## NATS / JetStream

### 优点

NATS 架构轻量、部署简单、消息延迟低。它使用 Subject 组织消息，支持通配符订阅，适合微服务通信、控制面消息和边缘节点。JetStream 在此基础上增加了持久化、确认、重放和消费状态管理。

### 缺点

NATS 的数据处理生态不如 Kafka，复杂业务消息能力不如 RocketMQ。对于长期海量存储、超大规模积压或复杂事务消息，通常不是首选。

### 适用场景

适合微服务事件通知、边缘计算、IoT、控制指令和对部署体量敏感的低延迟系统。

## 选型时需要确认的问题

选型前应明确消息是业务事件还是数据流，峰值和平均吞吐是多少，允许多大延迟和积压，是否需要事务、顺序、延迟、重试、回溯、多租户或跨地域能力，以及团队能够承担多高的运维复杂度。

可靠性配置也需要统一比较口径。例如副本数、同步刷盘、发布确认、消费确认和批量策略不同，性能结果会有明显差异。最终应使用真实消息大小、生产消费比例和故障模型进行压测。
